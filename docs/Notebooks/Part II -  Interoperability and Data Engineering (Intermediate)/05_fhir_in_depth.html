Health Informatics in R · Part II: Interoperability & Data Engineering · Module 5 of 16

FHIR (Fast Healthcare Interoperability Resources) is a standard describing data formats and elements (known as “resources”) and an API for exchanging electronic health records. the backbone of modern health-data exchange, so this module goes deep: the resource model, references that link resources, bundles that package them, search, and the SMART on FHIR authorization pattern that lets apps read from an EHR.

Learning objectives

By the end of this module you will be able to:

  1. Explain the FHIR resource model and how references stitch resources together.
  2. Build and validate Patient, Observation, and Condition resources from tabular data.
  3. Assemble the three bundle types you meet in practice: collection, transaction, searchset.
  4. Perform a FHIR search (simulated locally) and read a real server with a graceful fallback.
  5. Describe profiles/validation and the SMART on FHIR launch/authorization flow.

Note on version. The FHIR resources in this notebook are represented as plain R lists modeling FHIR R5 JSON. The concepts — resources, references, bundles, search — are identical in R4, which you’ll see most often in the wild.

Dataset

We reuse the synthetic EHR generator (identical to Part I) and turn a slice of it into real FHIR resources. Live-server calls target public sandboxes but fall back to local resources so the notebook always runs.

# --- Self-contained synthetic EHR generator (identical to Part I) ---
# This is the SAME generator from Module 1. We rebuild the fake hospital database
# here so this notebook can run on its own. Nothing here is a real patient.
library(dplyr)
library(tibble)

# This function generates a synthetic electronic health record (EHR) dataset.
# It creates mock tables for patients, encounters, observations, conditions, and medications,
# all with plausible structure, but not referencing any real patients or requiring external data.
make_synthetic_ehr <- function(n_patients = 200, seed = 42) {
  # Generate a small, internally-consistent synthetic EHR dataset.
  # Returns a list of linked tibbles: patients, encounters, observations,
  # conditions, and medications. This is for illustrative, educational use.
  set.seed(seed)  # same seed => same fake people every run

  # --- patients table ---
  # Create a tibble with n_patients patients, each with a name, sex, age, and birth year.
  first <- c("Ava","Liam","Noah","Mia","Zoe","Omar","Ivan","Sara","Leo","Nina",
             "Ruth","Kai","Yara","Theo","Ida","Sam","Ana","Eli","Rex","Uma")
  last  <- c("Khan","Ortiz","Chen","Diaz","Patel","Ali","Brown","Nash","Reed","Vega",
             "Cole","Frost","Grant","Hale","Iqbal","Jain","Kerr","Lund","Mora","Park")
  sexes <- sample(c("male", "female"), size = n_patients, replace = TRUE, prob = c(0.49, 0.51))
  ages  <- sample(18:89, size = n_patients, replace = TRUE)
  # Columns:
  #   patient_id  — unique ID, e.g. "P1000", "P1001"
  #   given_name / family_name — randomly chosen from the name lists
  #   sex, age — pre-generated vectors
  #   birth_year — derived from age, assuming the reference year 2026
  patients <- tibble(
    patient_id  = sprintf("P%d", 1000 + (0:(n_patients - 1))),
    given_name  = sample(first, size = n_patients, replace = TRUE),
    family_name = sample(last,  size = n_patients, replace = TRUE),
    sex         = sexes,
    age         = ages,
    birth_year  = 2026 - ages
  )

  # --- encounters table ---
  # Each patient gets 1–4 visits. Types and dates are random but internally consistent.
  #   encounter_id    — unique, zero-padded (E00001, E00002, ...)
  #   encounter_type  — ambulatory 55%, emergency 15%, inpatient 10%, wellness 20%
  #   date            — a random day in a 3-year window starting 2023-01-01
  enc_types <- c("ambulatory", "emergency", "inpatient", "wellness")
  enc_list <- vector("list", 0)
  n <- 0
  for (pid in patients$patient_id) {
    n_visits <- sample.int(4, 1)  # 1 to 4 encounters per patient
    for (j in seq_len(n_visits)) {
      n <- n + 1
      day <- sample(0:(365 * 3 - 1), 1)  # offset within 3 years
      enc_list[[n]] <- tibble(
        encounter_id = sprintf("E%05d", n),
        patient_id = pid,
        encounter_type = sample(enc_types, 1, prob = c(0.55, 0.15, 0.10, 0.20)),
        date = as.Date("2023-01-01") + day
      )
    }
  }
  encounters <- bind_rows(enc_list)

  # --- observations table ---
  # Labs and vitals attached to encounters. Each row is (name, unit, lo, hi).
  # A value is drawn uniformly in [lo, hi]; 70% of (encounter, measure) pairs exist
  # so the table looks sparse the way a real EHR does.
  obs_defs <- tribble(
    ~name, ~unit, ~lo, ~hi,
    "Body height", "cm", 150, 195,
    "Body weight", "kg", 50, 110,
    "Systolic blood pressure", "mmHg", 100, 165,
    "Heart rate", "/min", 55, 100,
    "Hemoglobin A1c", "%", 4.8, 9.5
  )
  obs_list <- vector("list", 0)
  m <- 0
  for (i in seq_len(nrow(encounters))) {
    e <- encounters[i, ]
    for (k in seq_len(nrow(obs_defs))) {
      if (runif(1) < 0.7) {
        m <- m + 1
        obs_list[[m]] <- tibble(
          observation_id = sprintf("O%06d", m),
          encounter_id = e$encounter_id,
          patient_id = e$patient_id,
          observation = obs_defs$name[k],
          value = round(runif(1, obs_defs$lo[k], obs_defs$hi[k]), 1),
          unit = obs_defs$unit[k],
          date = e$date
        )
      }
    }
  }
  observations <- bind_rows(obs_list)

  # --- conditions table ---
  # Each patient is assigned 0–3 unique diagnoses from a small pool.
  cond_pool <- c("Essential hypertension", "Type 2 diabetes mellitus", "Asthma",
                 "Acute bronchitis", "Major depressive disorder", "Osteoarthritis",
                 "Chronic kidney disease", "Anemia")
  cond_list <- vector("list", 0)
  cn <- 0
  for (pid in patients$patient_id) {
    n_cond <- sample(0:3, 1)
    if (n_cond > 0) {
      chosen <- sample(cond_pool, size = n_cond, replace = FALSE)
      for (cc in chosen) {
        cn <- cn + 1
        cond_list[[cn]] <- tibble(condition_id = sprintf("C%05d", cn), patient_id = pid, condition = cc)
      }
    }
  }
  conditions <- bind_rows(cond_list)

  # --- medications table ---
  # Same pattern as conditions: 0–3 unique drugs per patient.
  med_pool <- c("Lisinopril", "Metformin", "Albuterol", "Atorvastatin",
                "Sertraline", "Amoxicillin", "Ibuprofen", "Hydrochlorothiazide")
  med_list <- vector("list", 0)
  mn <- 0
  for (pid in patients$patient_id) {
    n_med <- sample(0:3, 1)
    if (n_med > 0) {
      chosen <- sample(med_pool, size = n_med, replace = FALSE)
      for (mm in chosen) {
        mn <- mn + 1
        med_list[[mn]] <- tibble(medication_id = sprintf("M%05d", mn), patient_id = pid, medication = mm)
      }
    }
  }
  medications <- bind_rows(med_list)

  list(
    patients = patients,
    encounters = encounters,
    observations = observations,
    conditions = conditions,
    medications = medications
  )
}

5.1 The resource model and references

In FHIR, information is separated into distinct building blocks called resources. These resources do not contain other resources directly; instead, they are linked by references using the pattern ResourceType/id. For example, an Observation resource links to its associated patient through a reference like subject: Patient/P1001. This referencing mechanism enables systems to piece together a complete health record from separately stored resources, rather than relying on deeply nested or monolithic data structures.

# A FHIR resource is a JSON (or XML) object with a defined schema: resourceType,
# id, name, gender, birthDate, ...  We represent it as a plain nested named list
# in R — this *is* how FHIR JSON looks, so a named list is a faithful,
# dependency-free stand-in for a schema-validating library like Python's
# fhir.resources. We build one from a row in our table.
library(jsonlite)

# Pick a patient with a Hemoglobin A1c reading among their observations, so the
# examples below (and the search demo in 5.3) have something to find.
pid_with_a1c <- ehr$observations %>%
  filter(observation == "Hemoglobin A1c") %>%
  pull(patient_id) %>%
  unique() %>%
  .[1]

row <- ehr$patients %>% filter(patient_id == pid_with_a1c) %>% slice(1)

# Build a Patient resource from that row.
# name is a list of lists because a person can have several names (official, maiden, nickname).
# given is also a list: some people have more than one given name.
# birthDate uses YYYY-MM-DD; we only know the year, so we use January 1 as a stand-in.
patient <- list(
  resourceType = "Patient",
  id = row$patient_id,
  name = list(list(use = "official",
                    family = row$family_name,
                    given = list(row$given_name))),
  gender = row$sex,
  birthDate = sprintf("%d-01-01", row$birth_year)
)

# toJSON() serializes the list to FHIR JSON (pretty = TRUE makes it readable)
cat(toJSON(patient, auto_unbox = TRUE, pretty = TRUE))

  "id": "P1000",

    {
      "use": "official",
      "family": "Brown",
      "given": [
        "Eli"
      ]
    }
  ],
  "gender": "male",

# An Observation resource is FHIR's version of a lab result or vital sign.
# The CODE (LOINC) is what makes the observation interoperable — the same
# 4548-4 means "Hemoglobin A1c" in every FHIR system, not just ours.
#
# LOINC maps our human-readable observation names to official codes.
LOINC <- c(
  "Hemoglobin A1c" = "4548-4",
  "Systolic blood pressure" = "8480-6",
  "Heart rate" = "8867-4",
  "Body weight" = "29463-7",
  "Body height" = "8302-2"
)

pid <- row$patient_id  # e.g. "P1000" — the same person as the Patient above

# filter() keeps only this patient's observations. We order so the Hemoglobin
# A1c reading (guaranteed to exist for this patient) sorts first, then keep
# the first four rows so the example stays small.
pt_obs <- ehr$observations %>%
  filter(patient_id == pid) %>%
  arrange(desc(observation == "Hemoglobin A1c")) %>%
  head(4)

obs_resources <- vector("list", nrow(pt_obs))
for (i in seq_len(nrow(pt_obs))) {  # walk each observation row
  o <- pt_obs[i, ]
  obs_resources[[i]] <- list(
    resourceType = "Observation",
    status = "final",  # the result is complete, not a preliminary draft
    # code.coding is a list so one observation can be tagged with several systems
    code = list(coding = list(list(system = "http://loinc.org",
                                    code = unname(LOINC[o$observation]),
                                    display = o$observation))),
    # subject.reference points at the Patient resource we built above.
    # The pattern is always ResourceType/id — that is the FHIR "pointer".
    subject = list(reference = sprintf("Patient/%s", pid)),
    effectiveDateTime = as.character(o$date),  # when the measurement was taken
    # valueQuantity holds the number and the unit
    valueQuantity = list(value = o$value, unit = o$unit)
  )
}

cat(sprintf("Built %d Observation resources, all referencing Patient/%s\n", length(obs_resources), pid))
Built 4 Observation resources, all referencing Patient/P1000
cat("\nExample subject reference:", obs_resources[[1]]$subject$reference, "\n")

5.2 Bundles: collection, transaction, searchset

A Bundle in FHIR is a resource that groups together multiple other resources into a single package. The meaning of a Bundle depends on its type field, which defines how its contents should be interpreted:

  • collection: Represents a simple group of resources bundled together, such as a set of related documents or a snapshot of information.
  • transaction: Specifies a batch of operations that should be performed together in a single, atomic action on a FHIR server—meaning either all succeed or none are applied. Each item in the bundle includes instructions on what to do (in a request field).
  • searchset: Represents the results from a FHIR server search query. When you ask a FHIR server to search for resources, it responds with a Bundle of type searchset containing the matching resources.
# A Bundle packages several resources into one payload.
# type="transaction" means: apply every entry as a write, all-or-nothing.
# If any entry fails on the server, none of them should be saved.
#
# Each entry needs two pieces:
#   resource  — the FHIR resource itself
#   request   — the HTTP method and URL the server should execute

# PUT Patient/{id} → create-or-replace this patient (idempotent: same id, same result)
tx_entries <- list(
  list(resource = patient, request = list(method = "PUT", url = sprintf("Patient/%s", pid)))
)

# POST Observation → create a new observation; the server assigns the id
for (obs in obs_resources) {
  tx_entries[[length(tx_entries) + 1]] <- list(resource = obs,
                                                request = list(method = "POST", url = "Observation"))
}

transaction <- list(resourceType = "Bundle", type = "transaction", entry = tx_entries)

5.3 FHIR search - simulated locally

In FHIR, performing a search typically involves making an HTTP GET request such as: [base]/Observation?subject=Patient/P1001&code=4548-4 This instructs the FHIR server to return all Observation resources associated with subject Patient/P1001 and the specific code 4548-4. The server responds with a Bundle of type searchset, which contains the results matching the search criteria. In this example, we mimic this search functionality locally by iterating through our in-memory resources, allowing you to understand how FHIR servers process searches without requiring a live server connection.

# A real FHIR search is an HTTP GET like:
#   [base]/Observation?subject=Patient/P1001&code=4548-4
# The server returns a Bundle with type="searchset".
#
# We don't need a live server to see the mechanics. This function walks an
# in-memory list of resources and applies the same two filters a server would:
#   subject  — whose record is this?  (Patient/P1001)
#   code     — which LOINC (or other) code?
fhir_search <- function(resources, resource_type, subject = NULL, code = NULL) {
  # Minimal FHIR-style search over in-memory resources -> searchset Bundle.
  hits <- list()
  for (r in resources) {
    # Skip anything that isn't the requested resource type (Patient vs Observation)
    if (r$resourceType != resource_type) next
    ok <- TRUE
    # subject filter: Observation.subject.reference must match exactly
    if (!is.null(subject)) {
      ok <- ok && (!is.null(r$subject) && identical(r$subject$reference, subject))
    }
    # code filter: look inside code.coding[] for the requested code
    if (!is.null(code)) {
      codes <- if (!is.null(r$code)) sapply(r$code$coding, function(c) c$code) else character(0)
      ok <- ok && (code %in% codes)
    }
    if (ok) hits[[length(hits) + 1]] <- r
  }
  # A searchset Bundle carries the matching resources plus a total count
  list(resourceType = "Bundle", type = "searchset", total = length(hits),
       entry = lapply(hits, function(h) list(resource = h)))
}

# Search the patient + their observations as if they were a tiny FHIR server
pool <- c(list(patient), obs_resources)
result <- fhir_search(pool, "Observation", subject = sprintf("Patient/%s", pid), code = "4548-4")

cat(sprintf("GET [base]/Observation?subject=Patient/%s&code=4548-4\n", pid))
GET [base]/Observation?subject=Patient/P1000&code=4548-4
cat("searchset total:", result$total, "\n")

for (e in result$entry) {

  cat(sprintf("  -> %s: %s %s\n", e$resource$code$coding[[1]]$display, q$value, q$unit))
}

5.4 Reading from a real server — with a fallback explained

In the context of FHIR and real-world notebooks: when fetching resources from public sandboxes (such as HAPI), you would typically use the httr package for HTTP calls. However, notebooks are sometimes unable to access external servers, which could cause code to fail. To prevent this, well-designed tutorial code uses “graceful degradation”: if a live server can’t be reached, it falls back to using local data, ensuring the notebook still works and doesn’t crash.

# Against a public sandbox (e.g. HAPI FHIR) you read a resource with HTTP GET:
#   GET https://hapi.fhir.org/baseR5/Patient/P1001
#   Accept: application/fhir+json
#
# Tutorial notebooks often can't reach the internet, so this function
# degrades gracefully: try the live server, and if anything fails (timeout,
# DNS, non-200, ...), return the local Patient we already built.
library(httr)

get_patient_live <- function(base, pid, timeout_s = 5) {
  # Try a live FHIR read; fall back to the local resource on any failure.
  tryCatch({
    r <- GET(
      sprintf("%s/Patient/%s", base, pid),
      add_headers(Accept = "application/fhir+json"),  # ask for FHIR JSON, not HTML
      timeout(timeout_s)  # don't hang forever if the sandbox is down
    )
    if (status_code(r) == 200) {  # 200 = the resource was found
      list(source = "live", data = content(r, as = "parsed", type = "application/json"))
    } else {
      stop("non-200 response")  # fall through to local data via the error handler
    }
  }, error = function(e) {
    # network error, timeout, non-200, etc. — fall back to the local resource.
    # `patient` here is the dict-like list form of our local Patient (same
    # shape as live JSON) built earlier in the notebook.
    list(source = "fallback", data = patient)
  })
}

res <- get_patient_live("https://hapi.fhir.org/baseR5", pid)
cat(sprintf("source: %s\n", res$source))
source: fallback
cat("patient family name:", res$data$name[[1]]$family, "\n")
patient family name: Brown 
cat("\n(The REST pattern is identical against any FHIR server; only the base URL changes.)\n")

5.5 Profiles and validation

A FHIR profile is a set of rules that further restricts or customizes the base FHIR specification for a particular context or country. For example, the US Core profile specifies that certain fields in a Patient resource are required for use in the United States.

Validation is the process of checking that a FHIR resource adheres to its schema and any applicable profile. In this notebook we check the base FHIR schema with a small hand-written validate_observation() function whenever we build a resource. If you provide invalid or incomplete data, it immediately stop()s with a clear error. This explicit validation step is a critical first step to ensure that the data you’re working with is correct and trustworthy (you’ll see more on advanced data quality in Module 8).

# We enforce the FHIR schema by hand, at construction time.
# Observation.status is a coded field: it must be one of
#   registered | preliminary | final | amended | corrected | cancelled | ...
# Passing a made-up value stop()s with a clear message instead of silently
# shipping a broken resource. That is your first data-quality gate.
validate_observation <- function(res) {
  allowed_status <- c("registered", "preliminary", "final", "amended",
                       "corrected", "cancelled", "entered-in-error", "unknown")
  if (!(res$status %in% allowed_status)) {
    stop(sprintf(
      "1 validation error for Observation\nstatus\n  Input should be a valid FHIR observation-status code, got '%s'",
      res$status
    ))
  }
  res
}

tryCatch({
  bad <- validate_observation(list(
    resourceType = "Observation",
    status = "not-a-real-status",  # invalid — FHIR does not allow this string
    code = list(coding = list(list(code = "x")))
  ))
}, error = function(e) {
  cat("Schema validation rejected the resource:\n")
  cat(" ", strsplit(conditionMessage(e), "\n")[[1]][1], "\n")  # first line of the error is enough
  cat("  -> 'status' must be a valid FHIR observation-status code\n")
})

5.6 What is SMART on FHIR? How do apps connect?

SMART on FHIR is a specification that allows third-party applications to securely connect to electronic health record (EHR) systems. It does this by combining FHIR (for accessing health data) with OAuth2 (for authorization and user consent).

Here’s how the SMART on FHIR authorization process typically works:

  1. Launch – The EHR launches an app, providing both a launch token and the FHIR server’s base URL.
  2. Authorize – The app redirects the user to the EHR’s OAuth2 authorization page, asking for specific “scopes” (permissions), for example, the ability to read a patient’s Observations (patient/Observation.read).
  3. Token – After the user approves, the app receives an authorization code, which it exchanges with the EHR for an access token.
  4. Call – The app makes FHIR API requests to the server, including Authorization: Bearer <token> in the HTTP header; this proves the app’s identity and defines which data it is allowed to access.
# SMART on FHIR's last step is an ordinary FHIR search with an extra header:
#   Authorization: Bearer <access_token>
# The token is what the EHR issued after the user authorized the app.
# Scopes on that token (e.g. patient/Observation.read) decide what the
# server will actually return.
#
# We don't make a live call here — we just show the request you would send.
authorized_search <- function(base, token, path) {
  headers <- list(
    Authorization = sprintf("Bearer %s", token),  # proves the app is allowed to read
    Accept = "application/fhir+json"
  )
  # Live version would be: httr::GET(sprintf("%s/%s", base, path), add_headers(...))
  sprintf("GET %s/%s  [Authorization: Bearer <token>]", base, path)
}

cat(authorized_search(
  "https://ehr.example/fhir",
  "TOKEN",
  sprintf("Observation?patient=%s&code=4548-4", pid)
))
GET https://ehr.example/fhir/Observation?patient=P1000&code=4548-4  [Authorization: Bearer <token>]

Key takeaways

  • FHIR records are modular resources linked by references, not one big blob.
  • Bundle type (collection/transaction/searchset) determines what the bundle does.
  • Search is HTTP; the returned searchset bundle is the unit of exchange.
  • Schema validation is free with a small hand-written check function; SMART on FHIR is how apps obtain scoped access.
