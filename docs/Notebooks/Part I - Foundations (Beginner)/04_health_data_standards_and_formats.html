Health Informatics in R · Part I: Foundations · Module 4 of 16

Data that can’t move between systems isn’t much use. Interoperability standards define how a patient record is packaged so a receiving system can understand it. This module walks the ladder from flat files up through HL7 v2, CDA, and FHIR, parsing each in R.

Learning objectives

By the end of this module you will be able to:

  1. Place the main health-data formats on a spectrum from flat files → HL7 v2 → CDA → FHIR and say when each is used.
  2. Parse an HL7 v2 message and pull structured values out of it.
  3. Parse a CDA document (XML) with xml2.
  4. Construct and serialize FHIR resources as plain nested R lists.
  5. Represent the same patient fact across all three modern standards.

Dataset

We use small, hand-built sample messages — one HL7 v2 lab result, one CDA fragment, and FHIR resources we construct in code. They all describe the same synthetic patient (Ava Khan, A1c 7.2%) so you can watch one fact change costume.

4.1 The interoperability ladder

Format Era / use Shape Strength
Flat file (CSV) Bulk extracts, research Rows & columns Simple, universal
HL7 v2 Real-time messaging (still dominant in hospitals) Pipe-delimited segments Ubiquitous, battle-tested
CDA Clinical documents (discharge summaries) XML Human- + machine-readable docs
FHIR Modern APIs, apps, exchange JSON/XML resources + REST Web-native, granular, extensible

Reality check: HL7 v2 still carries the majority of live hospital messaging, while FHIR is where new development happens. You will meet both for years.

4.2 Flat files - the baseline

# A FLAT FILE is the simplest health-data format: rows and columns, like a spreadsheet.
# Easy to parse, but it carries almost no standard meaning - nothing here says

#
# read.csv(text = csv) pretends a string is a file, so R can read it

library(dplyr)
library(tibble)

P1001,Hemoglobin A1c,7.2,%
P1001,Systolic blood pressure,148,mmHg"

4.3 HL7 v2 - segments and fields

An HL7 v2 message is a set of segments (lines), each split into fields by |, with ^ separating components. MSH is the header, PID the patient, OBX an observation. It looks archaic but it’s everywhere.

# An HL7 v2 message is a text blob hospitals still use for real-time lab results,
# ADT (admit/discharge/transfer) events, and orders. It looks cryptic. Here is
# how to read it:
#
#   Each LINE is a SEGMENT (MSH, PID, OBR, OBX, ...)
#   Fields inside a segment are split by the pipe character |
#   Pieces inside a field are split by ^
#
#   MSH = message header (who sent it, what kind of message, version)
#   PID = patient identification (ID, name, date of birth, sex, address)
#   OBR = order/observation request (which test was ordered)
#   OBX = observation result (the actual lab/vital value)
#
# This sample says: Ava Khan (P1001) has A1c 7.2% (high) and SBP 148 mmHg (high).
hl7_msg <- "MSH|^~\\&|LAB|CENTRAL_HOSP|EHR|CENTRAL_HOSP|20260115093000||ORU^R01|MSG00001|P|2.5
PID|1||P1001^^^HOSP^MR||Khan^Ava^L||19680312|F|||12 Elm St^^Ithaca^NY^14850
OBR|1|||4548-4^Hemoglobin A1c^LN
OBX|1|NM|4548-4^Hemoglobin A1c^LN||7.2|%|4.0-5.6|H|||F
OBX|2|NM|8480-6^Systolic blood pressure^LN||148|mmHg|90-120|H|||F"
cat(hl7_msg, "\n")
MSH|^~\&|LAB|CENTRAL_HOSP|EHR|CENTRAL_HOSP|20260115093000||ORU^R01|MSG00001|P|2.5
PID|1||P1001^^^HOSP^MR||Khan^Ava^L||19680312|F|||12 Elm St^^Ithaca^NY^14850
OBR|1|||4548-4^Hemoglobin A1c^LN
OBX|1|NM|4548-4^Hemoglobin A1c^LN||7.2|%|4.0-5.6|H|||F
OBX|2|NM|8480-6^Systolic blood pressure^LN||148|mmHg|90-120|H|||F 
# There is no CRAN package needed here — this is realistically how HL7 v2 is
# hand-parsed: split the message into segments, then split each segment into
# fields.
#
# Real HL7 v2 messages separate segments with a carriage return (\r), not a
# normal newline (\n). Our sample used newlines so it would display nicely,
# so we convert them before parsing.
raw <- gsub("\n", "\r", hl7_msg)
seg_lines <- strsplit(raw, "\r")[[1]]

# Split each segment line on the pipe character to get its fields.
h <- lapply(seg_lines, function(s) strsplit(s, "\\|")[[1]])

# Each segment's first field is its 3-letter name (MSH, PID, OBR, OBX, ...)
seg_names <- sapply(h, function(s) s[1])
cat("Segments present:", paste(seg_names, collapse = ", "), "\n")
Segments present: MSH, PID, OBR, OBX, OBX 
# get_field(seg, n) returns HL7 field n (1-indexed, per the HL7 spec) from a
# segment vector. Field n sits at R index n + 1, because index 1 holds the
# segment name itself (PID, OBX, ...).
get_field <- function(seg, n) {
  idx <- n + 1
  if (idx <= length(seg)) seg[idx] else ""
}

# the PID (patient identification) segment.
# Fields are numbered from 1 in the spec; get_field() uses the same numbering.
#   PID-5 = patient name (Khan^Ava^L  →  family^given^middle)
#   PID-7 = date of birth (YYYYMMDD)
#   PID-8 = sex
pid <- h[[which(seg_names == "PID")]]
cat("\nPatient name (PID-5):", get_field(pid, 5), "\n")

Patient name (PID-5): Khan^Ava^L 
cat("Patient DOB  (PID-7):", get_field(pid, 7), "\n")
Patient DOB  (PID-7): 19680312 
cat("Patient sex  (PID-8):", get_field(pid, 8), "\n")
Patient sex  (PID-8): F

Milestone 1 - extract all OBX results into a table

# Walk every segment in the parsed message. When we find an OBX (a result),
# pull out the useful fields and collect them into a tibble.
#
# Inside an OBX, the important field numbers are:
#   OBX-3 = observation identifier  (LOINC^name^coding-system, split by ^)
#   OBX-5 = the value               (e.g. 7.2)
#   OBX-6 = the unit                (e.g. %)
#   OBX-8 = abnormal flag           (H = high, L = low, N = normal)
obx_rows <- list()
for (seg in h) {
  if (seg[1] == "OBX") {
    code_field <- get_field(seg, 3)  # e.g. "4548-4^Hemoglobin A1c^LN"
    # split on ^ : piece 1 is the LOINC code, piece 2 is the display name
    pieces <- strsplit(code_field, "\\^")[[1]]
    loinc <- pieces[1]
    name  <- pieces[2]
    obx_rows[[length(obx_rows) + 1]] <- tibble(
      loinc       = loinc,
      observation = name,
      value       = get_field(seg, 5),
      unit        = get_field(seg, 6),
      flag        = get_field(seg, 8)
    )
  }
}

obx <- bind_rows(obx_rows)
cat("Structured results parsed from HL7 v2 OBX segments:\n")
Structured results parsed from HL7 v2 OBX segments:
print(as.data.frame(obx), row.names = FALSE)
  loinc             observation value unit flag
 4548-4          Hemoglobin A1c   7.2    %    H
 8480-6 Systolic blood pressure   148 mmHg    H

4.4 CDA - clinical documents in XML

A CDA (Clinical Document Architecture) document is XML with a fixed header and structured body. It represents whole documents — discharge summaries, referral notes. We parse a minimal fragment with xml2.

# CDA (Clinical Document Architecture) is XML: nested tags instead of pipes.
# It is used for whole documents (discharge summaries, referral notes) that a
# human can also open and read.
#
# The important nested pieces in this fragment:
#   <id extension="P1001"/>              → patient ID
#   <given>Ava</given><family>Khan</family>  → name
#   <administrativeGenderCode code="F"/> → sex
#   <birthTime value="19680312"/>        → date of birth
#   <code code="4548-4" .../>            → LOINC for A1c
#   <value unit="%" value="7.2"/>        → the result
#
# xmlns="urn:hl7-org:v3" is the CDA namespace — we will need it when we search.
cda <- '<?xml version="1.0"?>
<ClinicalDocument xmlns="urn:hl7-org:v3">
  <recordTarget>
    <patientRole>
      <id extension="P1001"/>
      <patient>
        <name><given>Ava</given><family>Khan</family></name>
        <administrativeGenderCode code="F"/>
        <birthTime value="19680312"/>
      </patient>
    </patientRole>
  </recordTarget>
  <component>
    <observation>
      <code code="4548-4" codeSystemName="LOINC" displayName="Hemoglobin A1c"/>
      <value unit="%" value="7.2"/>
    </observation>
  </component>
</ClinicalDocument>'
cat(substr(cda, 1, 180), "...\n")  # print just the start so you see the shape without a wall of XML
<?xml version="1.0"?>
<ClinicalDocument xmlns="urn:hl7-org:v3">
  <recordTarget>
    <patientRole>
      <id extension="P1001"/>
      <patient>
        <name><given>Ava</given><fa ...
# xml2 is a CRAN package (a wrapper around libxml2) — no extra install beyond
# what this series already uses. It turns the XML string into a tree of nodes
# we can search.
library(xml2)

# CDA tags live in a namespace. xml_find_first() needs that namespace or it
# will find nothing. We give it a short nickname "v3" so paths can say
# v3:patient, v3:name, etc.
ns <- c(v3 = "urn:hl7-org:v3")

doc <- read_xml(cda)  # parse the XML string into a tree; doc is <ClinicalDocument>

# .// means "search anywhere below the root". Paths walk the nested tags.
# xml_text()       = the words between a tag pair, e.g. <given>Ava</given> → "Ava"
# xml_attr(x, "code") = an attribute on the tag, e.g. code="F" → "F"
given  <- xml_text(xml_find_first(doc, ".//v3:patient/v3:name/v3:given", ns))
family <- xml_text(xml_find_first(doc, ".//v3:patient/v3:name/v3:family", ns))
sex    <- xml_attr(xml_find_first(doc, ".//v3:administrativeGenderCode", ns), "code")
dob    <- xml_attr(xml_find_first(doc, ".//v3:birthTime", ns), "value")
obs    <- xml_attr(xml_find_first(doc, ".//v3:observation/v3:code", ns), "displayName")
val    <- xml_find_first(doc, ".//v3:observation/v3:value", ns)

cat(sprintf("Patient : %s %s  (sex=%s, dob=%s)\n", given, family, sex, dob))
Patient : Ava Khan  (sex=F, dob=19680312)
cat(sprintf("Observation: %s = %s %s\n", obs, xml_attr(val, "value"), xml_attr(val, "unit")))
Observation: Hemoglobin A1c = 7.2 %

4.5 FHIR - resources and REST

FHIR breaks the record into modular resources (Patient, Observation, Condition, …) exchanged as JSON/XML over a REST API. It is the modern standard and the one you’ll build against most. We construct resources as plain nested R lists — this is how FHIR JSON looks, so a named list is a faithful, dependency-free stand-in — and validate required fields with small hand-written check functions instead of pydantic.

# FHIR breaks the record into modular RESOURCES. A Patient resource is a
# JSON (or XML) object with a defined schema: id, name, gender, birthDate, ...
#
# Here a Patient resource is:
#   1. built as a named R list with the same keys/nesting FHIR JSON uses
#   2. checked against the required fields with a small hand-written validator
#   3. serialized back to JSON with jsonlite for sending over an API
library(jsonlite)

# A small hand-written validator standing in for what fhir.resources checks
# via pydantic in Python: confirm the required fields are present.
validate_patient <- function(p) {
  required <- c("resourceType", "id")
  missing_fields <- setdiff(required, names(p))
  if (length(missing_fields) > 0) {
    stop("Invalid Patient resource, missing required field(s): ",
         paste(missing_fields, collapse = ", "))
  }
  invisible(TRUE)
}

# Build one Patient resource for Ava Khan — the same person as in the HL7/CDA samples.
# name is a list of lists because a person can have several names (official, maiden, nickname).
patient <- list(
  resourceType = "Patient",
  id = "P1001",
  name = list(list(family = "Khan", given = list("Ava"), use = "official")),
  gender = "female",
  birthDate = "1968-03-12"
)
validate_patient(patient)

# toJSON() serializes the list to FHIR JSON (pretty=TRUE for readability;
# auto_unbox=TRUE makes single-element vectors print as scalars, not arrays)
cat(toJSON(patient, auto_unbox = TRUE, pretty = TRUE))
{
  "resourceType": "Patient",
  "id": "P1001",
  "name": [
    {
      "family": "Khan",
      "given": [
        "Ava"
      ],
      "use": "official"
    }
  ],
  "gender": "female",
  "birthDate": "1968-03-12"
}
# An Observation resource is FHIR's version of a lab result or vital sign.
# Notice the same LOINC code (4548-4) and the same 7.2% as in HL7 and CDA —
# the CODE is what makes the three formats talk about the same fact.
validate_observation <- function(o) {
  required <- c("resourceType", "id", "status", "code")
  missing_fields <- setdiff(required, names(o))
  if (length(missing_fields) > 0) {
    stop("Invalid Observation resource, missing required field(s): ",
         paste(missing_fields, collapse = ", "))
  }
  invisible(TRUE)
}

a1c <- list(
  resourceType = "Observation",
  id = "obs-a1c-1",
  status = "final",  # the result is complete, not a preliminary draft
  # code.coding is a list so one observation can be tagged with several systems
  code = list(coding = list(list(system = "http://loinc.org",
                                  code = "4548-4",
                                  display = "Hemoglobin A1c"))),
  # subject.reference points at the Patient resource we built above
  subject = list(reference = "Patient/P1001"),
  # valueQuantity holds the number, the unit, and the UCUM unit system
  valueQuantity = list(value = 7.2, unit = "%",
                       system = "http://unitsofmeasure.org", code = "%")
)
validate_observation(a1c)
cat(toJSON(a1c, auto_unbox = TRUE, pretty = TRUE))
{
  "resourceType": "Observation",
  "id": "obs-a1c-1",
  "status": "final",
  "code": {
    "coding": [
      {
        "system": "http://loinc.org",
        "code": "4548-4",
        "display": "Hemoglobin A1c"
      }
    ]
  },
  "subject": {
    "reference": "Patient/P1001"
  },
  "valueQuantity": {
    "value": 7.2,
    "unit": "%",
    "system": "http://unitsofmeasure.org",
    "code": "%"
  }
}

Milestone 2 - bundle resources for exchange

In FHIR, a Bundle groups multiple resources together, allowing them to be exchanged as a single package between systems (for example, when sending the results of a batch query or submitting multiple records in one API call).

bundle <- list(
  resourceType = "Bundle",
  type = "collection",
  entry = list(
    list(resource = patient, fullUrl = "Patient/P1001"),
    list(resource = a1c,     fullUrl = "Observation/obs-a1c-1")
  )
)
cat("Bundle type:", bundle$type, "\n")
Bundle type: collection 
cat("Entries    :", length(bundle$entry), "\n")
Entries    : 2 
cat("First entry resourceType:", bundle$entry[[1]]$resource$resourceType, "\n")
First entry resourceType: Patient 
cat("\nA FHIR Bundle is what a server returns from a query and what apps POST back.\n")

Milestone 3 - the same fact in three standards

Here we illustrate how a single clinical fact, Ava Khan’s A1c is 7.2%, can be represented using three different healthcare data standards: HL7 v2, CDA (an XML-based standard), and FHIR (a modern JSON-based standard). Although each format has its own structure, they all use the same standardized LOINC code (4548-4) and value to represent the fact, enabling interoperability across systems.

# Same clinical fact — Ava Khan's A1c is 7.2% — in three packaging standards.
# The LOINC code 4548-4 is the glue; only the envelope changes.
cat("HL7 v2 (OBX):\n")
HL7 v2 (OBX):
cat("  OBX|1|NM|4548-4^Hemoglobin A1c^LN||7.2|%|4.0-5.6|H\n")
  OBX|1|NM|4548-4^Hemoglobin A1c^LN||7.2|%|4.0-5.6|H
cat("\nCDA (XML):\n")

CDA (XML):
cat('  <observation><code code="4548-4" .../><value unit="%" value="7.2"/></observation>\n')
  <observation><code code="4548-4" .../><value unit="%" value="7.2"/></observation>
cat("\nFHIR (JSON):\n")

FHIR (JSON):
cat('  {"code":{"coding":[{"system":"http://loinc.org","code":"4548-4"}]},\n')
  {"code":{"coding":[{"system":"http://loinc.org","code":"4548-4"}]},
cat('   "valueQuantity":{"value":7.2,"unit":"%"}}\n')
   "valueQuantity":{"value":7.2,"unit":"%"}}
cat("\nSame LOINC 4548-4, same 7.2% — three packaging standards.\n")

Key takeaways

  • Formats climb a ladder: flat file → HL7 v2 → CDA → FHIR, each trading simplicity for richer, more interoperable semantics.
  • HL7 v2 still dominates live messaging; FHIR is where new work happens — learn both.
  • The same coded fact travels across all of them; codes (Module 3) are the glue that makes exchange meaningful.
